## 0. 사용자 지적
1. 6장 전체가 내용이 제각각이고 장의 주장이 보이지 않음
2. "발표 준비" 절(두 문장)은 무엇을 말하는지, 필요한 내용인지 알 수 없음. 필요하다면 "AI로 발표 자료를 만드는 방법" 또는 "발표 자료 구성 방법"이 있어야 함
3. 프로젝트 관리 예제(사내 교육 과정 온라인 전환)가 어색함. SI 방식의 자체 LLM 구성과 RAG 구축 프로젝트로 바꿀 것

## 1. 현재 6장 흐름 진단
### 1-1. 절 순서와 문제

|---|---|---|---|
| 1 | 업무 영역별 활용 | 업무 전반 | 장 첫 절로 적합 |

| 15 | 산업별 확인 항목 | **조직** | 창작 뒤 장 끝에 홀로 있음. 3번(도입 단계)과 같은 조직 수준 |

### 1-2. 장의 주장이 보이지 않는 이유
- 장 첫 문단의 주장("초안, 정리, 분석, 아이디어는 AI가, 최종 판단과 발송은 사람이")이 있으나, 절들이 업무, 조직, 창작 수준을 오가며 섞여 있어 주장이 이어지지 않음
- 요점 상자 세 줄(정책이 허용한 도구, 맡기는 방식, 창작 구조)도 절 묶음과 대응하지 않음
- 묶음마다 "이 묶음이 장의 주장을 어떻게 보여 주는가"를 말하는 연결 문장이 없음

## 2. 재구성안: 네 묶음, 각 묶음의 주장
장의 주장은 그대로 둡니다: **AI는 초안을 만들고 사람은 판단한다.** 네 묶음이 각각 이 주장을 한 측면에서 보여 줍니다.

| 묶음(h2) | 주장(묶음 첫 문장) | 들어가는 절(h3) |
|---|---|---|
| 1. 업무에 맡기기 전에 정할 것 | `업무에 AI를 사용하기 전에 무엇을 맡기고, 어떤 데이터를 입력하고, 어디까지 맡기지 않을지를 먼저 정합니다.` | 업무 영역별 활용(표 6-1), AI에 맡기는 방식(표 6-2), 입력 데이터 관리(표 6-5→6-3), 사람에게 영향을 주는 업무의 한계(옛 "인사 업무의 한계") |
| 2. 업무 유형별 활용 | `업무 문서는 구조와 근거를 사람이 정하고, AI는 그 틀 안에서 초안과 계산을 맡습니다.` | 데이터 분석(표 6-6→6-4), 기획서 초안과 전략 분석, 업무 소통(메일 초안), 발표 자료 만들기(신설, 4절) |
| 3. 프로젝트 관리 | `프로젝트 관리에서 AI는 단계별 문서 초안을 만들고, 범위, 일정, 위험, 결정은 프로젝트 매니저가 확정합니다.` | 그림 6-1, 착수, 작업 분해, 일정, 위험 관리, 진척 보고, 프로젝트 매니저의 역할(예제를 3절의 SI 구축 프로젝트로 교체) |
| 4. 창작 | `창작은 사람이 구조를 정하고 AI에게 부분 초안을 맡기며, 결과를 사용하기 전에 권리를 확인합니다.` | 생성 유형(표 6-7), 창작 작업 절차, 이야기 구성, 플랫폼별 콘텐츠(표 6-8), 이미지 프롬프트 구성(표 6-9) |
| 5. 조직으로 넓히기 | `개인의 사용을 조직으로 넓힐 때는 도입 단계에 맞춰 통제를 늘리고, 자기 산업의 조건을 확인합니다.` | 도입 단계(표 6-3→6-10), 산업별 확인 항목 |
- 묶음 5에서 표 6-4(에이전트 도입 단계별 통제)는 3절 SI 프로젝트의 운영 이관 단계와 8장 에이전트 자율성으로 흡수하고 6장에서는 삭제합니다(8장과 중복 해소). 삭제가 부담스러우면 묶음 5 안에 그대로 둡니다(작성 A 판단).
- 장 첫 문단은 유지하고, 둘째 문장 뒤에 `이 장은 맡기기 전에 정할 것, 업무 유형별 활용, 프로젝트 관리, 창작, 조직으로 넓히기의 순서로 이 원칙을 적용합니다.`를 추가합니다.
- 요점 상자 세 줄 교체: `업무에 맡기기 전에 맡길 범위와 입력할 데이터를 정합니다.` / `업무 문서와 프로젝트 문서는 AI가 초안을 만들고, 구조와 결정은 사람이 정합니다.` / `창작은 구조를 사람이 정하고, 결과를 사용하기 전에 권리를 확인합니다.`
- 표 번호는 새 순서로 다시 매기고 id, 다른 쪽 참조(7장 과제의 "표 6-4", 8장의 "Chapter 6 표 6-4" 등)와 번호 뒤 조사를 함께 고칩니다. 예: 입력 데이터 분류는 표 6-3이 됨

## 3. 프로젝트 관리 예제 교체: 사내 규정 질의응답 시스템 구축(SI, 가상)
### 3-1. 프로젝트 소개 문단(교체)
`이 절은 가상의 SI 프로젝트 하나를 단계마다 이어서 예로 듭니다. 예제는 사내 규정과 업무 매뉴얼에 대한 질문에 근거 문서와 함께 답하는 질의응답 시스템 구축 프로젝트입니다. 회사 데이터를 외부로 보낼 수 없어 오픈 가중치 모델을 사내 서버에서 운영하고, 검색 증강 생성(Chapter 4)으로 문서를 검색해 답합니다. 기간은 16주, 투입 인원은 프로젝트 매니저를 포함해 8명입니다. 예제의 프로젝트와 수치는 모두 가상의 예입니다.`
- 다른 장과의 연결: 오픈 가중치 모델 선택(7장), 검색 증강 생성과 교차 검증(4장), 프롬프트 인젝션과 권한(8장)

### 3-2. 착수
```
다음 메모를 바탕으로 프로젝트 착수 문서 초안을 작성해 줘.
항목은 목적, 범위 안, 범위 밖, 성공 기준, 이해관계자, 주요 제약으로 나눠 줘.
메모에 없는 내용은 '확인 필요'로 표시해 줘.

<메모>
- 목적: 직원이 사내 규정과 업무 매뉴얼을 질문하면 근거 문서와 함께 답하는 시스템 구축
- 기간 16주, 투입 8명(프로젝트 매니저, 아키텍트, 데이터 엔지니어 2명, 백엔드 개발자 2명, 화면 개발자, 품질 담당), 예산 4억 원
- 회사 데이터는 외부로 반출할 수 없음. 오픈 가중치 모델을 사내 GPU 서버에서 운영
- 대상 문서: 규정, 지침, 매뉴얼 약 3,000건(PDF와 한글 문서가 섞여 있음)
- 이번 범위 밖: 사내 메신저 연동, 문서 자동 작성 기능
- 보안팀은 부서별 문서 접근 권한을 답변에도 그대로 적용하기를 요구함(적용 방법은 미정)
</메모>
```
- 기대 결과 설명(교체): `기대할 수 있는 결과의 예에서는 메신저 연동과 문서 자동 작성이 범위 밖에 들어가고, 메모에 없는 성공 기준과 이해관계자는 '확인 필요'로 표시되며, 부서별 접근 권한의 적용 방법은 범위는 정해졌지만 방법이 정해지지 않은 항목으로 '확인 필요'가 됩니다. AI는 메모에 적힌 내용으로 초안을 만들 뿐, 이해관계자가 실제로 기대하는 것까지는 알지 못합니다. 프로젝트 매니저는 의뢰 부서, 보안팀, 인프라팀과 직접 확인해 범위 안과 밖을 합의하고, "시험 질문 200개 가운데 정답률 85% 이상, 답변마다 근거 문서 표시"처럼 측정할 수 있는 성공 기준을 확정합니다.`

### 3-3. 작업 분해
```
착수 문서의 범위 안 항목을 산출물 기준으로 3단계까지 나눠 줘.
마지막 단계는 한 사람이 1주 안에 끝낼 수 있는 크기로 나눠 줘.
분해한 뒤, 범위 안 항목 가운데 어느 작업에도 포함되지 않은 것을 따로 적어 줘.
```
- 기대 결과 설명(교체): `기대할 수 있는 결과의 예에서는 문서 수집과 변환(형식 변환, 조각 나누기), 검색 색인(임베딩 생성, 벡터 저장소 구성), 모델 운영 환경(GPU 서버 설치, 모델 선정과 성능 시험), 질의응답 기능(검색과 생성 연결, 근거 표시), 화면, 권한 연동, 평가(시험 질문 세트 작성과 채점), 운영 이관 같은 작업이 나오고, 문서마다 관리 부서와 공개 범위를 확인하는 작업처럼 어느 산출물에도 연결되지 않은 항목이 따로 표시됩니다. 프로젝트 매니저는 작업 크기가 팀원의 숙련도와 맞는지, 보안 심의와 장비 반입 승인처럼 조직의 승인 절차가 작업으로 들어 있는지 확인합니다. 진척을 확인하기 어려울 만큼 큰 작업은 더 나누고, 지나치게 잘게 나뉘어 관리 부담만 늘리는 작업은 묶습니다.`

### 3-4. 일정
```
아래 작업 목록과 기간으로 16주 일정표를 만들어 줘.
열은 주차, 작업, 담당, 선행 작업으로 하고, 4주, 8주, 12주, 16주 끝에 마일스톤을 표시해 줘.
선행 작업이 끝나기 전에 시작하는 작업이 있으면 표 아래에 따로 적어 줘.

<작업>
1. 문서 수집과 변환(3주, 데이터 엔지니어 2명)
2. GPU 서버 반입과 설치(4주, 인프라팀, 구매 승인 뒤)
3. 모델 선정과 성능 시험(3주, 2 완료 후)
4. 검색 색인 구축(3주, 1 완료 후)
5. 질의응답 기능과 화면 개발(5주, 3과 4 완료 후)
6. 권한 연동(3주, 보안팀의 적용 방식 확정 후)
7. 시험 질문 200개 평가(2주, 5 완료 후)
8. 시범 운영(2주, 7 통과 후)
</작업>
```
- 기대 결과 설명(교체): `기대할 수 있는 결과의 예에서는 문서 수집과 변환이 1~3주, GPU 서버가 1~4주, 검색 색인이 4~6주, 모델 선정이 5~7주, 질의응답 기능과 화면이 8~12주, 평가가 13~14주, 시범 운영이 15~16주에 배치되고, 권한 연동은 보안팀의 결정 시점을 알 수 없어 표 아래에 따로 적힙니다. 이 배치에는 여유 기간이 하루도 없습니다. 프로젝트 매니저는 장비 구매 승인과 보안 심의에 걸리는 기간, 특정 담당자가 투입될 수 있는 시기, 공휴일처럼 목록에 없는 제약을 반영하고, 지연에 대비한 여유 기간을 두어 실행할 수 있는 마일스톤을 확정합니다.`
- 검산: 1(1~3), 2(1~4), 4(4~6, 1 뒤), 3(5~7, 2 뒤), 5(8~12, 3과 4 뒤), 7(13~14), 8(15~16) → 16주, 임계 경로 2→3→5→7→8

### 3-5. 위험 관리
- 프롬프트는 현재 그대로 사용
- 기대 결과 설명(교체): `기대할 수 있는 결과의 예에서는 문서 변환 품질 저하, 모델 답변 정확도 미달, 일정 지연 같은 흔한 위험이 나열됩니다. 프로젝트 매니저는 담당 칸을 실제 담당자로 채우고, 이 조직에만 있는 위험을 추가합니다. 예를 들어 GPU 서버 구매 승인 지연, 문서 관리 부서의 공개 거부, 인사 시스템의 조직도와 문서 권한 체계의 불일치, 규정 개정이 색인에 늦게 반영되어 옛 규정으로 답하는 위험, 근거를 확인하지 않고 답을 그대로 믿는 사용자 문제(Chapter 4 자동화 편향)입니다. AI가 보지 못한 위험을 찾는 일이 이 단계에서 프로젝트 매니저가 맡는 몫입니다. 목록은 진척 보고 때마다 다시 점검합니다.`

### 3-6. 진척 보고
```
아래 이번 주 작업 기록으로 주간 보고를 작성해 줘.
순서는 요청 사항, 완료, 진행, 지연, 다음 주 계획으로 하고, 지연 항목에는 원인과 대응을 한 줄씩 적어 줘.
기록에 없는 수치는 포함하지 마.

<기록>
- 문서 3,000건 가운데 2,100건 변환 완료, 한글 문서 표 깨짐 320건 재작업 중
- GPU 서버 반입이 구매 심의 일정으로 2주 늦어짐
- 모델 후보 2종을 기존 개발 서버에서 소형 모델로 먼저 시험 중
- 보안팀의 권한 적용 방식 미확정(결정 회의 일정 없음)
</기록>
```
- 기대 결과 설명(교체): `기대할 수 있는 결과의 예에서는 요청 사항에 권한 적용 방식 결정 회의 개최와 서버 구매 심의 일정 앞당기기가 먼저 나오고, 지연 항목에 서버 반입 지연과 대응(기존 개발 서버에서 소형 모델로 먼저 시험)이 적힙니다. 프로젝트 매니저는 서버 지연이 모델 선정과 기능 개발로 이어지는 임계 경로에 있어 마일스톤에 영향을 주는지 판단하고, 보고의 수치가 작업 기록과 같은지 대조합니다. 일정을 변경하거나 인력을 다시 배치하는 결정은 AI 초안이 아니라 프로젝트 매니저가 내립니다.`

## 4. 발표 자료 만들기 (옛 "발표 준비" 대체)
**판정**: 현재 두 문장은 방법도 예제도 없어 무엇을 하라는지 알 수 없습니다. 발표 자료는 업무에서 자주 만드는 문서이므로 절을 유지하되, AI로 발표 자료를 만드는 순서와 구성 원칙, 예제를 갖춘 절로 다시 씁니다. 예제는 3절 SI 프로젝트의 착수 보고회로 하여 묶음 2와 3을 잇습니다(묶음 3 뒤에 두거나, 묶음 2에 두고 "Chapter 6 프로젝트 관리의 착수 문서"를 참조).

**본문(교체)**
`발표 자료는 AI에게 슬라이드를 바로 만들게 하지 않고, 핵심 메시지와 구성을 먼저 정한 뒤 슬라이드별로 요청합니다. 처음부터 슬라이드를 요청하면 정보를 나열한 자료가 되어 청중이 결론과 결정할 일을 찾기 어렵기 때문입니다. 작업은 다음 순서로 진행합니다.`
1. `발표 목적, 청중, 발표 시간, 청중이 이 발표에서 결정할 일을 입력합니다.`
2. `발표 전체의 핵심 메시지를 한 문장으로 받고 사람이 확정합니다.`
3. `슬라이드 구성을 받습니다. 슬라이드마다 제목은 주장 한 문장, 본문은 근거 세 개 이내로 하고, 사용할 그림이나 표를 제안하게 합니다.`
4. `결정이 필요한 내용은 앞부분에 두고, 청중별 예상 질문과 답변 초안을 함께 받습니다.`
5. `사람이 순서와 강조점을 정하고, 수치는 원자료와 대조한 뒤 문장을 다듬습니다. 슬라이드 생성 기능이 있는 도구는 확정한 구성을 화면으로 옮길 때 사용합니다.`

**예제**
```
아래 착수 문서를 바탕으로 착수 보고회 발표 자료의 구성을 만들어 줘.

<조건>
- 발표 20분, 질의응답 10분
- 청중: 의뢰 부서장 3명, 보안팀장, 인프라팀장, 현업 담당자 10명
- 이번 보고회에서 결정할 일: 성공 기준(시험 질문 정답률) 확정, 문서 접근 권한 적용 방식 결정
</조건>

1. 발표 전체의 핵심 메시지를 한 문장으로 적어 줘.
2. 슬라이드를 10장 안으로 구성하고, 장마다 제목은 주장 한 문장, 본문은 근거 세 개 이내로 적고, 사용할 그림이나 표를 제안해 줘.
3. 결정이 필요한 두 가지는 앞부분에 배치해 줘.
4. 보안팀장과 인프라팀장이 할 만한 질문 다섯 개와 답변 초안을 적어 줘.

<착수 문서>
(착수 단계에서 확정한 착수 문서)
</착수 문서>
```
**기대 결과 설명**: `기대할 수 있는 결과의 예에서는 "사내 문서를 외부로 보내지 않고 근거와 함께 답하는 규정 질의응답 시스템을 16주 안에 시범 운영합니다" 같은 핵심 메시지와, 2~3장에 성공 기준과 권한 방식의 결정 요청이 놓인 구성이 나옵니다. 예상 질문에는 "답변에 권한 밖 문서가 섞이지 않는가", "GPU 서버 반입이 늦어지면 일정은 어떻게 되는가" 같은 질문이 포함됩니다. 사람은 청중이 가장 먼저 알아야 할 내용을 기준으로 순서를 정하고, 수치와 일정이 착수 문서와 같은지 확인합니다.`
